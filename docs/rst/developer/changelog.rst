Unreleased
----------

Fixed
~~~~~

- **Market figure label.** The two labels of ``Market_interaction.png`` read *Sport price*; they now read *Spot price*.
- **Docs build without the heavy libraries.** ``conf.py`` imported ``el1xr_opt`` before the autodoc mocks were active. The import failed part way and left a half-loaded package, so a later autodoc import of ``oM_InputData`` hit a circular import. It did not show on CI, but it failed a local build with only the docs requirements. The half-loaded modules are now dropped, and the option-indicator table loads ``oM_Features.py`` on its own.
- **The command line exits with 0 after a successful run.** ``el1xr-run`` and ``python -m el1xr_opt`` passed the model returned by ``main()`` to ``SystemExit``, so every finished run exited with code 1, and a script or CI step could not tell it from a failure. A new ``cli()`` runs ``main()`` and returns 0; a failed run still raises and exits with 1. ``main()`` still returns the model for Python callers.
- **``data/Home1`` runs again.** The copy of Home1 in ``data/`` was an older version of the case in the package: it had no ``VarFixedAvailability`` file and one ``FCRN`` reserve column instead of ``FCRN_Up`` and ``FCRN_Down``, so ``--dir data --case Home1`` stopped with a ``KeyError``. Its files now match the package's Home1, which solves to optimal (4713.8 SEK), and a test keeps the two in step. The Quickstart now gives the real defaults of the command line: ``--dir`` is the package folder, ``--indlog`` is ``True``, and an argument left out is asked for.
- **Documentation errors.** The examples page now describes the shipped cases as they are and gives the exact run commands. The data page describes each data file by its layout (unit table, time series or single-row table), lists the optional tables, and marks the files that are read but not used. Five math symbols that were not defined now are, and three tariff parameters that shared one symbol have their own. The option-indicator table on the features page is written from the code at every build, so it lists all 21 indicators. The retailer buy and sell limits are described as the code applies them: only when positive. Smaller fixes: the project layout, the API list (``oM_TimeBlocks``), the version shown in the docs, the Projects page (Horizon Europe), the Installation page (release and main can differ), a finished roadmap item, and the markup of the results page.
- **Activated reserve energy could not reach the meter.** The retailer balance ``eEleRetNodeBalance`` counted the scheduled output and charge of a battery or a thermal generator, while the physical balance ``eEleBalance`` counts the totals, which include the activated reserve energy. Since the audit C14 fix both balances are tied to the meter (``eEleImportBuyLink``, ``eEleExportSellLink``). So any FCR activation of such a unit with a non-zero net duty was infeasible, and the model held the battery's FCR bids to levels where it was not. The retailer balance now counts each unit of the retailer once, with its total output and charge, as the physical balance does. This also counts a unit that is in neither the RES, thermal nor storage set (a fuel cell), and counts a battery with a constant cost once rather than twice. The validation and sizing goldens are unchanged. On Home1 with battery FCR the cost falls from 340.825556 to 339.462884. Guarded by ``tests/test_formulation_fixes.py::test_retail_balance_carries_the_activated_reserve_energy``.
- Formulation bugs found in the model audit (``tests/test_formulation_fixes.py`` guards each):

  - **Hydrogen O&M cost sign.** ``eTotalHydGCost`` subtracted the O&M variable cost where the electricity analogue adds it, so the model was effectively paid to run hydrogen generators. Now added.
  - **Hydrogen storage inventory never built.** ``eHydInventory`` was gated on ``model.negs`` -- the *electricity* storage cycle set -- instead of ``model.nhgs``, so it was silently skipped and hydrogen state-of-charge went untracked (the storage could discharge hydrogen it never stored). Now gated on the hydrogen set. This only affects cases where the hydrogen units are active in the base year; on the shipped cases the hydrogen units are out of the base year, so the headline goldens are unchanged. It does correct the ``H2Tank`` / ``Electrolyser`` variant cases, which now reveal a separate gap: the hydrogen production path does not fully serve their demand, so they are marked ``xfail`` until the hydrogen sizing path is built out.
  - **Ramp-down parameter typo.** The ``eEleMaxRampDwOutput`` guard read ``pEleGenRampDw`` (a parameter that exists nowhere) instead of ``pEleGenRampDown``, which would ``KeyError`` for any thermal unit with a ramp-down limit under ``IndBinGenRamps == 1``. No shipped case has a thermal generator, so the bug was latent.
  - **Hydrogen demand ignored the base-year period.** The hydrogen demand set ``model.hd`` selected units whose ``MaximumPower`` was zero and applied no period window, so a hydrogen demand whose ``InitialPeriod`` / ``FinalPeriod`` does not cover the base year was active anyway (while the matching hydrogen supply was correctly excluded). It now applies the same base-year period test as electricity demand and the generation sets. Hydrogen demand is driven by the ``VarMaxDemand`` time series rather than a ``MaximumPower`` cap, so there is no ``MaximumPower > 0`` filter. The shipped hydrogen demand is zero in the base year, so the goldens are unchanged; ``make_sizing_cases`` now also brings the variant cases' hydrogen demand into the base year, alongside the supply it already moved.
  - **Heat operating cost not duration-weighted.** ``HeatOperatingCost`` (heat-not-served and generator running cost) was discounted by period but not weighted by the load-level duration, unlike the electricity and hydrogen operating costs, so it was mis-scaled on representative load levels that stand in for several hours. Now multiplied by ``pDuration`` per level.
  - **Candidate electrolyser sized on the wrong capacity.** An electrolyser (e2h) makes hydrogen from electricity at ``output = input / ProductionFunction``, so its production is set by the *electricity input*. The investment layer capped only the hydrogen-*output* nameplate (``eHydInvestMaxOutput``), leaving the electricity input fixed at its operating bound, so building a larger candidate electrolyser bought no extra production. A new ``eHydInvestMaxCharge`` caps the electricity input by the build decision too (analogous to ``eEleInvestMaxCharge`` for storage), so the input capacity -- the real design variable -- scales with the investment. It applies only to candidate e2h units, so the goldens are unchanged. (Making the variant cases actually serve their hydrogen demand needs two further case-level fixes -- a finite storage cap on the tank and a cost on the electricity import at the converter node -- so ``H2Tank`` / ``Electrolyser`` stay ``xfail`` for now.)
  - **Hydrogen storage energy missed the factor1 unit conversion.** The ``factor1`` knob converts storage-*energy* units at the point of use: the electricity inventory variable bounds (``oM_InputData``) and the candidate-storage cap (``eEleInvestMaxInventory``) both scale by it, and the initial inventory (``pHydInitialInventory = GenInitialStorage * factor1``) is scaled for both sectors. The hydrogen inventory bounds and ``eHydInvestMaxInventory`` did **not** scale, so the hydrogen storage cap was in raw units while its initial state and accumulated inventory (built from factor1-scaled charge/inflow powers) were in scaled units -- inconsistent when ``factor1 != 1``. The hydrogen inventory bounds and the investment cap now scale by ``factor1`` like the electricity ones. ``factor1`` is 1.0 by default, so the goldens are unchanged; the fix is guarded at the source in ``tests/test_formulation_fixes.py``.
  - **Hydrogen storage charge/discharge roles swapped.** The hydrogen ESS mirrored the electricity ESS incorrectly: the 2nd-block limits gated output by the *charge* binary and charge by the *discharge* binary (``eHydMaxESSOutput2ndBlock`` / ``eMaxHydESSCharge2ndBlock``), and the charge/discharge decisions normalized by the wrong capacity (charging by the output power ``pHydMaxPower``, discharging by the charge capacity ``pHydMaxCharge``; ``eHydChargingDecision`` / ``eHydDischargingDecision``). Because ``eHydStorageMode`` makes charging and discharging mutually exclusive, the two binary swaps forced the storage 2nd block to zero whenever it actually charged or discharged. All four now follow the electricity convention (output ↔ discharge binary ↔ output power; charge ↔ charge binary ↔ charge capacity), confirmed against the ``conf.py`` symbol definitions. The shipped cases have no active base-year hydrogen storage, so the goldens are unchanged; the fix corrects the H2 variant cases.
  - **Thermal-store inventory not duration-weighted.** ``eHeatInventory`` updated the store as ``inv = prev + eff*charge - discharge`` with no load-level duration, unlike the electricity/hydrogen inventory balances (which sum ``duration * (...)``) and the heat operating cost (which the earlier fix made duration-weighted). So on a representative load level standing for several hours, a heat charge/discharge moved the store by one hour's worth while its cost counted all the hours -- the store state and its cost disagreed. The inventory now weights the charge/discharge by ``pDuration`` (``eHeatBalance`` stays a duration-free power balance, like ``eEleBalance``). The temporal-Benders heat boundary (``_rep_ht`` in ``oM_Decomposition``) is weighted to match. The shipped validation cases have no heat sector, and the heat tests use hourly resolution, so results are unchanged at ``duration = 1``; the fix corrects representative-period cases.
  - **Fuel-cell node lookup used an undefined set.** The hydrogen balance filtered the fuel-cell (h2e) hydrogen draw with ``model.n2g``, which does not exist -- only ``model.n2eg`` and ``model.n2hg`` do. A fuel cell is an electricity generator, so its node membership is in ``model.n2eg`` (mirroring how the electrolyser, a hydrogen generator, is looked up in ``model.n2hg`` on the electricity side). No shipped case has a fuel cell, so the bug was latent; the first one would have crashed or silently dropped the draw from the node balance. Now reads ``model.n2eg``.
  - **Thermal FCR-N output used storage-only reserve variables.** The generator branches of ``eEleTotalOutput`` adjusted output by the FCR-N discharge variables (``NorUpDis`` / ``NorDownDis``), which are declared on storage only, instead of the generator variables (``NorUpGen`` / ``NorDownGen``) the FCR-D legs in the same branches already used. The first committed thermal unit would have raised ``KeyError`` at build. No shipped case has a thermal generator, so the bug was latent. The generator branches now use the generator FCR-N variables.
  - **Pre-horizon commitment fixing used a stale loop variable.** The loop that fixes a unit's initial commitment from its ``UpTimeZero`` / ``DownTimeZero`` tested ``model.n.ord(n)`` with ``n`` left over from an earlier loop that only runs in multi-node mode, rather than the current index's own load level. In single-node mode (every shipped case) the first unit with a positive initial up/down time would have raised ``NameError``; otherwise the fixing was applied at the wrong load level. It now reads the index's own level, ``idx[-2]``. No shipped case has a unit with a positive initial up/down time, so the goldens are unchanged.
  - **Standby columns had no missing-column default.** ``StandByStatus`` and ``StandByPower`` (added with the three-state electrolyser feature) were read unconditionally, so an older hydrogen-generation file without them would ``KeyError`` -- unlike the FCR columns added at the same time, which default to "off". They now default to standby disabled (status 0, draw 0), so files predating the feature load unchanged.
  - **Storage charge-reserve bounds could divide by zero.** ``eEleFreqUpChargeBound`` / ``eEleFreqDownChargeBound`` divide the charge-side reserve by the charge capacity ``pEleMaxCharge`` but, unlike the electrolyser analogue, did not skip the rule when that capacity is zero -- a discharge-only storage unit with the default FCR flags would have raised ``ZeroDivisionError`` at build. The rules now skip when the charge capacity is zero (the bound is vacuous there anyway).
  - **Variable O&M was counted twice.** ``pEleGenLinearVarCost`` / ``pHydGenLinearVarCost`` were built as ``LinearTerm*FuelCost + OMVariableCost`` -- already including the variable O&M cost -- yet ``eTotalEleGCost`` / ``eTotalHydGCost`` also added an explicit ``OMVariableCost*output`` term, so any unit with an O&M cost paid for it twice (the electrolyser, at ``OMVariableCost = 18.2``, paid 36.4 instead of 18.2 per kg of hydrogen). The earlier "hydrogen O&M sign" fix corrected the sign of the explicit term but it sat on top of the O&M already inside ``LinearVarCost``. ``LinearVarCost`` is now the fuel cost only (``LinearTerm*factor1*FuelCost``); the single explicit term carries O&M. This also removes a secondary double-scaling: ``OMVariableCost`` is in ``idx_gen_factoring`` (scaled by ``factor1`` once at read), so the old ``+ OMVariableCost*factor1`` in the construction scaled it a second time -- the explicit term uses the singly-scaled value, which is correct. Only the electrolyser carries an O&M cost, and the only cases with an active, producing electrolyser are the ``H2Tank`` / ``Electrolyser`` cases (``xfail``) and the electrolyser demo cases (whose tests check the standby decision and the FCR wiring, not a cost), so no enforced golden moves; it does halve the O&M the electrolyser pays in those cases.
  - **Electrolyser FCR-down headroom was not state-gated.** The down-reserve headroom of an electrolyser (``eEleFreqDownChargeHeadroomConv``) was bounded by the bare nameplate ``pHydMaxCharge`` minus the flexible block, so an off or standby unit -- which cannot absorb the activation from cold -- could still sell its full nameplate as FCR-down, and a committed unit's room was overstated by its minimum load. The bound is now ``pHydMaxCharge2ndBlock * commitment - 2nd block``: off/standby units (commitment 0) get zero headroom, and a committed unit's room is its true free 2nd-block capacity. Also, a node with FCR-flagged electrolysers but no hydrogen store now forces the down bids to zero (empty endurance right-hand side) instead of skipping the endurance constraint.
  - **Standby was reachable from off, so a cold start could be dodged.** Nothing required the stack to be warm before entering standby, so the solver could go off -> standby (paying one period of standby draw) -> on and skip the cold-start cost. A new transition constraint ``sb[t] <= uc[t-1] + sb[t-1]`` (with a pre-horizon ``pHydInitialStandBy`` state, default off) makes standby reachable only from on or standby.
  - **Retail settlement missed the electrolyser's minimum load and standby draw.** ``eEleRetNodeBalance`` subtracted only the electrolyser's flexible (2nd-block) consumption, while the physical balance and the thermal generators' committed minimum use the full load. It now subtracts the full ``vEleTotalCharge`` (minimum load + 2nd block + standby), so the committed-minimum and standby electricity must actually be bought -- standby is no longer free.
  - **An activated FCR bid changed nothing physically.** The storage branch of ``eEleTotalCharge`` adjusts the realised charge by the four operating-reserve activation terms, but the electrolyser branch had none, so an activated electrolyser bid delivered no energy and made no extra hydrogen while the FCR-down endurance still reserved storage for it. The four activation terms are now added to the electrolyser branch too.
  - **A zero-fuel-cost electrolyser paid no start-up cost.** The cold-start constraints are gated on the start-up cost alone, but the cost was summed only over ``hgt`` (units with a positive constant/fuel cost), so an electrolyser with zero fuel cost got the constraints but never paid. ``eTotalHydGCost`` now also bills the start-up cost for electrolysers outside ``hgt``. The shipped AEL has a positive fuel cost, so it was already billed; the goldens are unchanged.
  - **No ramp or minimum up/down-time limit on the electrolyser draw (documented choice).** An electrolyser is a fast-ramping load, so a per-hour ramp limit is non-binding at hourly resolution and is commonly omitted; cycling is deterred instead by the cold-start cost and the standby state. This is now stated in the electrolyser section of the constraints documentation (Hashmi et al. 2024; Mansouri and Bruninx 2026). No constraint change.
  - **Green-H2 matching counted the standby draw and ignored additionality.** ``eGreenH2Matching`` capped the electrolyser's *full* electricity draw -- including the standby auxiliary load, which makes no hydrogen -- by the output of *all* renewables. It now matches only the productive draw (total charge minus the standby draw, per EU 2023/1184 Art. 6) against an explicit renewable-to-electrolyser allocation (``vEleResToE2h``, capped per unit by ``eGreenH2AllocCap``) over the PPA-flagged additionality pool (all renewables only if none is flagged). The matching is only active with ``pParGreenH2Matching`` and an electrolyser present -- the four validation cases have the hydrogen units out of the base year, and the electrolyser demo cases are ``xfail`` or build-only, so no enforced golden moves. The allocation variable is the scaffold for a Guarantee-of-Origin certificate balance that would also stop a renewable MWh being both sold and matched (Mansouri and Bruninx 2026); in the present model, where electricity sales carry no green attribute, it is equivalent to the aggregate bound, so that refinement is left as a follow-up.
  - **Hydrogen charge cap was never applied.** The loop that sets the upper bound on ``vHydTotalCharge`` tested ``idx in model.hg`` with ``idx`` the full ``(period, scenario, level, unit)`` tuple -- always false, since ``model.hg`` holds bare unit names -- so the bound was never set and a hydrogen storage unit's charge was capped only where the 2nd-block constraints happen to bind. It now tests ``idx[-1]`` (the unit), like the electricity loop, so the charge is bounded by ``pHydMaxCharge``. No shipped non-hydrogen case has a hydrogen store, so the goldens are unchanged.
  - **Free, unpriced hydrogen import/export.** ``vHydImport`` / ``vHydExport`` carry no cost and are tied to a buy/sell only by the retail composition constraints, which are built only when a hydrogen retailer sets a positive per-step cap (``pHydRetMaxBuy/Sell``). The network fixing that zeroes them at non-reference nodes ran only in multi-node mode, so in single-node mode -- and at any node with no active priced hydrogen retailer -- hydrogen could be imported for free, silently absorbing any future hydrogen demand. They are now fixed to zero everywhere a priced hydrogen retailer does not compose them. The electricity side is unaffected (its import is priced through the grid-fee and energy-tax terms and closed by the retail balance). No shipped case prices a hydrogen retailer, so the goldens are unchanged.
  - **Demand-only nodes were silently dropped.** The build guards of ``eEleBalance`` / ``eHydBalance`` counted a node's units and lines but not its demand, so a node carrying only demand got no balance and its load vanished at zero cost (``ENS`` / ``HNS`` stayed zero). The guards now also count demand (``ed2n`` / ``hd2n``), so such a node prices its unserved energy or fails loudly. Every shipped node already carries a unit or line, so the goldens are unchanged.
  - **Hydrogen retail per-step caps had no missing-column default.** ``MaxBuy`` / ``MaxSell`` are optional retail columns; the hydrogen retail file omits them, so ``pHydRetMaxBuy`` / ``pHydRetMaxSell`` were never created and the first case to activate a hydrogen retailer would ``KeyError`` in ``eHydRetMaxBuy`` / ``eHydRetMaxSell``. They now default to 0.0 ("no cap", which the rules already skip) when the column is absent, for both carriers -- like the standby and FCR columns.
  - **Flexible hydrogen demand could become a paid sink.** Hydrogen-not-served was bounded by the maximum demand, not the demand actually scheduled, so for a flexible (curtailable) hydrogen demand ``vHydDemand - vHNS`` could go negative and the demand node would inject hydrogen for the unserved-energy reward. A new ``eHydNotServedCap`` caps ``vHNS <= vHydDemand`` for flexible hydrogen demand (for fixed demand the existing ``vHNS <= max`` bound already implies it). Hydrogen demand carries no shift parameter, so it is curtailment within ``[min, max]`` rather than a shift, and no electricity-style recovery balance applies. No shipped case has flexible hydrogen demand, so the goldens are unchanged.
  - **Compressor consumption was dead data.** ``MaxCompressorConsumption`` (the electricity needed to compress hydrogen into a store, per unit charged) was read and unit-factored but referenced by no variable, constraint or cost, so charging a hydrogen store drew no electricity -- a first-order term in any behind-the-meter hydrogen case. Charging a store now draws ``MaxCompressorConsumption * charge`` electricity as a load on the store's node (``eEleBalance``), and the node's balance is built where a store with a compressor sits even if it has no other electricity asset. The rate defaults to zero for a store without the column (or with a blank value), so a case without compression builds an identical balance. The four headline validation cases keep the hydrogen units out of the base year, so their goldens are unchanged; only the hydrogen sizing cases (``H2Tank`` / ``Electrolyser``, already ``xfail``) carry a compressor-bearing store in the base year. The rate is applied in the data's own units (``factor1`` is 1.0 by default, so no conversion); the shipped value (0.0012) reads as about 1.2 kWh/kgH2 if taken as MWh/kgH2, which is in the usual compression range, but the absolute units are the case author's to confirm.

- **Energy-not-served / hydrogen-not-served cost double-weighted by duration.** ``eTotalEleRCost`` / ``eTotalHydRCost`` multiplied the unserved-energy penalty by ``pDuration`` internally, then the term was aggregated again with the ``psn`` duration weight (its O&M siblings carry no internal duration), so unserved energy was priced at ``pDuration**2``. The internal duration is removed; the objective aggregation supplies the single weight. The validation cases serve all load (ENS = HNS = 0 at the optimum), so the goldens are unchanged; the fix only changes load-shed cases.
- **Hydrogen retail peak-tariff type had no missing-column default.** The peak-variable fixing loops read ``pHydRetTariffType``, but the hydrogen retail file carries no ``TariffType`` column, so the first case that activates a hydrogen retailer crashed with ``KeyError`` (the same optional-column family as the MaxBuy/MaxSell fix above). ``TariffType`` now defaults to ``''`` -- no peak tariff, so every peak variable of that retailer is fixed to zero -- for both carriers. Guarded in ``tests/test_formulation_fixes.py``.
- **Hydrogen peak indicators declared over the electricity retail sets.** ``vHydPeakGlobalInd`` / ``vHydPeakMonthInd`` / ``vHydPeakDayInd`` were declared over ``psner`` / ``psder`` / ``psdner`` (the *electricity* retailer sets) in both domain branches, and the no-peak fixing block iterated those sets too, so the hydrogen fixing loops raised ``KeyError`` as soon as the hydrogen and electricity retailer sets differed. They are now declared and fixed over ``psnhr`` / ``psdhr`` / ``psdnhr``. These indicators appear in no constraint yet (the hydrogen peak-tariff cost layer is unbuilt), so the change is structural only and the goldens are unchanged. Guarded in ``tests/test_formulation_fixes.py``.
- **Hydrogen sizing cases redesigned; their ``xfail`` marks removed.** The ``H2Tank`` / ``Electrolyser`` cases asked a ~0.9 kgH2/h electrolyser to serve 5 kgH2/h with no other source, so they were infeasible and ``xfail`` (this supersedes the "stay xfail for now" notes in the bullets above). ``make_sizing_cases.py`` now (1) moves the hydrogen retailer to the converter node with a buy allowance, so hydrogen can be imported there at a price -- cheap at night (40 per kg), expensive in the day (80 per kg), with the electrolyser's own cost (about 53 per kg) in between; (2) gives the tank finite ratings (10 kgH2/h, the base data has 900+) and an empty start with no minimum-inventory floor, because the floor and the initial fill do not scale with the build fraction, which forced a candidate tank to build itself; (3) turns green-hydrogen matching off in these two cases (the base case's ~0.2 kW rooftop solar cannot supply an electrolyser drawing kilowatts). Both cases now serve the demand in full and make real sizing decisions -- the tank builds fully on night-to-day arbitrage, the electrolyser builds a small fraction for the hours where producing beats importing -- and their goldens are enforced. The build decisions are asserted separately (``test_h2_sizing_decisions``), since the investment-cost share of the total cost is below the golden tolerance.

- **Up and down times with TimeStep.** With ``TimeStep`` > 1 the minimum up and down times of hydrogen units, and the time already served at the start (``UpTimeZero``, ``DownTimeZero``) of every unit, stayed in hours while the rules count load levels. They are now converted with the other time counts (see Added). Cases with ``TimeStep = 1`` are unchanged.

- **Calendar compressed with TimeStep.** The date of each load level was counted over the active levels only, so with ``TimeStep`` > 1 the dates ran too slowly: 48 hours at ``TimeStep = 4`` (12 levels of 4 hours) were dated as one day, ending at 11:00. Daily and monthly rules (depth of discharge, peak tariffs) then grouped the wrong levels. The calendar now comes from the timeline (see Added), where each active level is a block that also covers the inactive levels merged into it. Guarded in ``tests/test_time.py``. Cases with ``TimeStep = 1`` are unchanged.

- **Ramp degradation cost with load levels other than an hour.** The electrolyser cycling cost (``RampDegradationCost``) is a cost per kW of change in consumption, but it sat in a row the objective weights by the duration of the level. A change cost a quarter as much at quarter-hour levels, and ``TimeStep`` times as much with ``TimeStep`` > 1. The term is now divided by ``pDuration``, so a change costs the same at any level length. At hourly levels with ``TimeStep = 1``, which every shipped case uses, the cost is unchanged. Test in ``tests/test_paper_case_15min.py``.

Changed
~~~~~~~

- **The documentation follows the house writing rules.** Headings are noun phrases in sentence case, the pages describe the steps without addressing the reader, dash asides are written as parentheses, colons or new sentences, and the pages use the field's words: *option indicator*, *day-ahead price* and *renewable hydrogen*. The pass also found content errors, now fixed: two equations of the hydrogen store and two notes still described binaries that the code no longer swaps; ``el1xr-install-solvers`` installs only HiGHS, not CBC; and the Contributing page pointed at one test file instead of the two test tiers. A second, reading pass rewrote the overview page in the register of the field, and gave every illustration a caption that names what it shows.
- Ramps between blocks. A ramp limit bounds the change of a rate between two blocks by the ramp rate times the time between the block midpoints, (l1 + l2) / 2, as in Gao et al. (2025). For an output or charge declared in ``oM_Data_Resolution`` this applies at the first level of each block; before, a change between two declared blocks was allowed the ramp of one load level only. With levels of equal length and no declaration the rule is unchanged. On H2VPP (48 h) at quarter hours, with the EVs and the battery declared ``uniform 1h``, the cost is 360.087456, the cost of the hourly case, instead of 362.753016. Tests in ``tests/test_load_level_minutes.py``.

- FCR endurance looks back one hour at any load level length. The inventory at the end of a level backs the FCR bid of the level one hour earlier (a new parameter, ``pParEnduranceLag``, the number of levels in one hour, at least one). Before, the rules looked back one level, so at quarter hours a bid was backed by the inventory 15 min after its level instead of an hour. The bids of the last hour are backed by the last inventory. At hourly levels the rules are unchanged; at quarter hours they look back four levels. This applies to the battery (``eEleStorageEndurance*``), electrolyser (``eEleFreqDownEnduranceConv*``) and fuel-cell (``eEleFreqUpEnduranceFuelCell*``) endurance. Test in ``tests/test_paper_case_15min.py``.

- ``ShiftedSteps``, the demand shift window, is read in hours like the other time counts, not in load levels. The two are the same at hourly levels with ``TimeStep = 1``, which is every shipped case.
- Time-resolution wording follows the field: the docs, the README, the module comments and the time structure figure say *highest* and *lowest* common resolution (as Gao et al. do), not *finest* and *coarsest*. The functions ``finest_common`` and ``coarsest_common`` keep their names.
- **One time-label convention: the start of the period.** Load level ``t0001`` is the hour 00:00-01:00 and is now labelled 00:00 everywhere, as day-ahead and balancing market data are. Before, the internal calendar used the start, while the result files and the night-hour rule of the network tariff used the end (01:00).

  - Result timestamps (the ``Date`` columns) are one hour earlier than before.
  - The night-hour rule reads the clock hour at the start of the level, and night runs from ``StartNightTime`` up to, not including, ``EndNightTime``. With 22 and 6, night is now 22:00-06:00. Before, it was 21:00-06:00. In the validation cases the 21:00-22:00 hour sets no peak, so every golden cost is unchanged to the last digit.
  - The calendar starts at 1 January 00:00 of the model year, whatever the minute of the run date.

- Documentation reorganised for consistent numbering and equation placement. Section numbers now come from Sphinx (``:numbered:`` on the Concepts toctree, with ``numfig`` / ``math_numfig`` so labelled equations get section-prefixed numbers); the manual "1., 2., ..." numbers in the constraints page are removed. Each layer's equations now live on its own page: a new :doc:`/concepts/investment` page carries the build-fraction variable and the investment capacity caps, the heat-sector and community pages carry their balance/coupling equations, and the green-hydrogen matching equations join the energy-conversion section of the constraints page -- replacing the summary tables that duplicated those pages at the bottom of the constraints page. The changelog's literal ``###`` lines are proper subsection headings now. ``conf.py`` gains the heat, community, green-hydrogen and investment math macros, and drops a reference to a ``custom.js`` file that does not exist.
- Storage unit labels in docstrings made consistent with the data and the variables, for both carriers. Labels only -- no change to the model or the goldens.

- Per-block scenario subsetting in the Benders block build. Each block solves a single-scenario subproblem, but ``_build_block`` used to keep every scenario in the scenario dimension dict, so ``data_processing`` built every parameter over the full N-scenario set product -- for each of the N blocks, roughly quadratic in the scenario count. It now produces a genuine single-scenario case (the kept scenario is the only one in the dict, and the other scenarios' rows are dropped from the data files; the scenario column is detected by content, not position, so node-indexed files such as the networks are left untouched). The kept scenario's data, including its unnormalised probability, is unchanged, so the subproblem and the optimum are identical. End-to-end sequential Benders is about 2.4x faster at 8 scenarios, 3.7x at 16 and 5.1x at 24 (same optimum throughout); the new build scales about linearly with the blocks where the old one grew quadratically, so the gain widens with the scenario count, and it stacks with the process-parallel solve. Correctness is unchanged. The end-to-end saving is small, which is itself the useful finding: the build cost is dominated by ``data_processing`` (reading the multi-scenario data), not by model construction (about 2.9 s vs 3.3 s for the full build at eight scenarios). - Time structure module ``oM_Time``, the first step towards a fully flexible time resolution (Gao et al., Applied Energy 396 (2025) 126267). Time is counted in 1-minute base units from the start of each representative period. A resolution is an ordered list of time blocks over a period; it may be uniform (``uniform 15min``), follow the clock (``calendar day``) or be given block by block (``explicit 60,60,120``). The module computes the overlap of two resolutions in base units, the highest common resolution of several (for constraints on instantaneous values) and the lowest (for constraints on accumulated values), and resamples a series from one resolution to another (mean for a rate, proportional split for an amount). It has no Pyomo dependency. ``data_processing`` now builds the timeline (``model.timeline``) and the resolution of the load levels (``model.time_res['level']``), and the calendar is read from them. The model itself is unchanged: every variable and constraint still lives on the load levels. Tests in ``tests/test_time.py`` include the worked example of Gao et al., Section 2.
- Electrolyser FCR provision. An electrolyser is a controllable load, so it can sell frequency reserves by modulating its consumption: upward reserve (FCR-D up, and the upward leg of the symmetric FCR-N) by reducing it, downward reserve by increasing it. The formulation is the charge-side mirror of the storage one -- bid-equals-provision links, FCR-N symmetry, headroom against the second block and the maximum charge, and availability bounds -- plus one genuinely new piece: a bus-level endurance constraint for the downward direction. Sustaining a downward bid makes extra hydrogen, so the bids of the electrolysers at a bus (converted to hydrogen through the production function) must fit in the free headroom of the hydrogen storage units at that bus; a bus with no storage gets no downward provision, and upward provision needs no storage at all. Participation is opt-in per unit via the new hydrogen-generation columns ``NoFCRD`` / ``NoFCRN`` (with ``EnduranceFCRD`` / ``EnduranceFCRN`` in minutes); the columns default to "not participating", so existing cases and the goldens are unchanged. On the generated ``ElectrolyserFCR`` sizing case the objective drops by exactly the FCR revenue the electrolyser earns versus the same case with FCR off.
- Electrolyser three-state operation (on / standby / off) with cold starts, after Qiu et al. (2022, IEEE CIEEC). A unit with ``StandByStatus = 1`` can sit in a standby state that draws a small fixed power (``StandByPower``) to keep the stack warm and makes no hydrogen -- the conversion identity subtracts the standby draw before turning electricity into hydrogen. Turning on from off pays the start-up cost; turning on from standby is free, which is what makes standby worth paying for through a short idle period. The state logic is three constraints: on and standby are mutually exclusive (off is the remainder), a cold-start lower bound on the start-up binary, and a start-up-implies-on upper bound that pins the start-up to exactly the off-to-on transitions (this also gave the previously dangling electrolyser shut-down binary a definition: it is fixed to zero, since an electrolyser has no shut-down transition in this model). Standby is off by default, so the goldens are unchanged. A new ``ElectrolyserStandby`` sizing case demonstrates the choice on a demand burst with an idle hour in the middle: the optimum holds the unit in standby through the gap instead of paying a second cold start, and ``test_electrolyser_standby_selected`` guards it.
- Electrolysers are now pure loads. They previously inherited the dispatchable hydrogen-generator constraints (output blocks, output ramps, minimum up/down times, the start-up/shut-down balance, and the initial-commitment heuristic), which let inconsistent hydrogen-output ratings force an infeasible schedule even though the unit's output is fully determined by its electricity input. Those constraints now skip electrolysers; the hydrogen output follows the conversion identity alone. This removed four of the five infeasibility roots in the ``H2Tank`` / ``Electrolyser`` sizing cases (the fifth is a plain capacity shortfall: those cases ask for 5 kgH2/h from a ~0.13 kgH2/h hydrogen path, so they stay ``xfail`` until the cases are redesigned).
- Heat thermal storage coupled across the temporal Benders time windows (``oM_Decomposition.el1xr_temporal_benders``), so a heat case with a thermal store decomposes too. A thermal store carries heat inventory across a window boundary exactly like a battery, so its boundary inventory becomes a master linking variable -- the ``St`` variable, the heat analogue of the ``Se`` / ``Sh`` boundary inventories for electricity / hydrogen storage: the incoming boundary replaces the window's first-level store balance with one reading the master copy, and the outgoing boundary ties the window's last-level inventory to the master copy. ``load_heat_data`` reads the heat storage set and bounds onto the structure model (a no-op for a case with no heat sector). A heat case whose store cycles across the boundaries reproduces the monolith exactly for 2, 3 and 4 time blocks (``tests/test_benders_temporal_el1xr.py::test_el1xr_temporal_benders_heat_storage_matches_monolithic``); the previous guard that refused heat thermal storage is removed. With this, the temporal split is transversal to the heat sector (operating cost and storage), the hydrogen sector and the network representation; only an unforeseen aggregate charge outside the horizon-coupling registry is still refused. See ``docs/decomposition.md``.
- Horizon-coupling cost registry, so the temporal Benders is driven by descriptors instead of hard-coded electricity names (``oM_Features.seed_horizon_coupling`` + ``register_horizon_constant`` / ``register_horizon_threshold`` / ``register_horizon_unsupported``). The per-(period, scenario) charges that do not split by time window are now declared as descriptors of two shapes: a ``constant`` charge (the fixed network fee -- counted once in the master, removed from each window's recourse) and a ``threshold`` charge (the peak demand charge -- the per-subgroup sum of the N largest of a metered quantity, reformulated as the threshold-LP with a master linking variable per (subgroup, item)). ``seed_horizon_coupling`` reads the structure model and declares the built-in electricity charges (a Daily-tariff peak is marked unsupported so the split raises rather than mis-handles it); ``el1xr_temporal_benders`` consumes the descriptors generically and carries no electricity parameter or variable names. A new sector with such a charge adds its descriptor in ``seed_horizon_coupling`` rather than editing the decomposition; the unhandled-``"ps"``-term guard now reads ``TEMPORAL_HANDLED_PS_COST`` / ``_REV`` from ``oM_Features``. Behaviour is unchanged for electricity -- the same 13 temporal tests pass -- and the registry itself is unit-tested in ``tests/test_features.py``. See ``docs/decomposition.md``.
- Endogenous-import case for the temporal Benders, and transversality across sectors and network modes (``oM_Decomposition.el1xr_temporal_benders``). The earlier peak tests pin the grid import to a fixed profile, which checks the threshold LP but leaves the import out of the decision. A new test lets the optimiser choose it: a single-node case whose only supply is the grid, delivered through a battery that starts empty, so the model must import to meet demand and can charge the battery off-peak and discharge it into the demand spike, shaving the top-N import. Now the storage-boundary coupling and the peak threshold are both active and interacting, with the import chosen freely, and the temporal Benders still reproduces the binary monolith exactly for 2, 3 and 4 time blocks (``tests/test_benders_temporal_el1xr.py::test_el1xr_temporal_benders_endogenous_import_matches_monolithic``). The split couples the windows only through storage inventory and the registered aggregate costs, so it is transversal to the network representation (single-node / DC / linear three-phase change a window's own constraints, not the coupling, and there is no network-investment variable to put in the master today) and to the hydrogen sector (no horizon-coupling aggregate cost). The heat operating cost decomposes per window and is now added to the recourse, so heat without a thermal store is handled too. Two cases are refused rather than solved with a silently wrong objective: heat with a thermal store (it couples the windows like a battery and needs the same boundary linking, a follow-on) and any new per-(period, scenario) aggregate charge that is not a plain sum over load levels (the split checks the registered ``"ps"`` cost/revenue terms against the known set and raises on an unhandled one). See ``docs/decomposition.md``.
- Peak-demand charge handled in the temporal Benders solve (``oM_Decomposition.el1xr_temporal_benders``), validated against the binary monolith. The peak charge is the sum of the N largest grid imports per month, a horizon-wide quantity that does not split by time window. It is rewritten as a threshold LP using the identity that the sum of the N largest of ``{x_n}`` equals ``min over t of [ N*t + sum_n (x_n - t)_+ ]``: the scalar threshold ``t`` per (month, retailer) becomes a master linking variable (the master holds the ``N*t`` part and the peak coefficient), and each window adds its own ``sum_n (import_n - t)_+`` over its hours. This is a pure LP and, because the peak enters the objective as a positive cost being minimised, it reproduces the binary top-N selection exactly -- and more tightly than the model's own big-M peak constraints, whose LP relaxation underprices the peak. On a single-node case where the costed grid import is the only supply (so the peak is active), the temporal Benders reproduces the binary monolith exactly for 2, 3 and 4 time blocks (``tests/test_benders_temporal_el1xr.py``). A separate fix was needed to make this reliable: each block penalises its feasibility slack variables heavily, and at a loose solver feasibility tolerance the solver nudges those slacks just below zero to harvest a spurious ``penalty * tolerance`` reduction that poisoned the recourse value and the cuts; the recourse value reported to the Benders bound now counts only positive slack, and the subproblem solves use a tightened primal feasibility tolerance. See ``docs/decomposition.md``.
- Heat sector wired end to end through the CSV pipeline. A case carrying the heat tables (``oM_Data_HeatGeneration`` with a ``Type`` column -- HeatPump / Boiler / Heat2Ele / Storage --, ``oM_Data_HeatDemand``, ``oM_Data_VarMaxHeatDemand``) now builds and solves through ``el1xr-run``: ``load_heat_data`` reads the tables and populates the heat sets and parameters, ``create_heat_sector`` builds the formulation (now indexed by period/scenario/load level like the other sectors), the heat-pump electricity draw and heat-to-power output are folded into the electricity balance, and the heat operating cost (period-discounted) into the objective. It is a no-op for cases without heat tables, and the four validation cases are byte-for-byte unchanged (verified after each step). Validated by ``tests/test_heat_sector.py`` including an end-to-end build-and-solve of a heat-bearing case.
- Nodal home-heat sector (``oM_HeatSector.create_heat_sector``), fleshing out the previous scaffold in the same nodal style as electricity and hydrogen. It builds a behind-the-meter heat node: a heat demand met by an electric heat pump (heat = COP x electricity, the cross-sector coupling), a boiler, and a thermal store, with a nodal heat balance, store inventory dynamics, and heat-not-served. The heat-pump electricity draw is exposed via ``heat_electricity_load`` for the electricity balance, and the heat operating cost via ``optmodel.HeatOperatingCost``. It builds only when the case carries heat sets, so it is a no-op for electricity/hydrogen-only cases and the four validation cases are unchanged; it is wired into ``oM_Sequence`` after the green-hydrogen step. The loop can be open or closed: a heat pump alone is power-to-heat only (open), and adding a heat-to-power unit (``htw``, an ORC/CHP turbine -- the analogue of the hydrogen fuel cell, ``vHeatToEle`` = efficiency x heat consumed, exposed via ``heat_to_power_output`` for the electricity balance) closes the power-heat loop. Hydrogen is already closed-loop (``e2h`` electrolyser + ``h2e`` fuel cell); a case selects open or closed by which conversion units it includes. Validated by ``tests/test_heat_sector.py`` (balance, COP coupling, store conservation, heat pump preferred over boiler, and the heat-to-power closed loop). Connecting the CSV input pipeline to populate the heat sets (data_processing + the electricity-balance coupling term) is the remaining step. See the ``oM_HeatSector`` module docstring and ``oM_InputSchema`` heat stems.
- Balance-formulation flag (``oM_Features.BALANCE_MODES``, parameter ``BalanceMode`` / ``pParBalanceMode``). It selects how power conservation is written -- ``nodal`` (one balance per node; the default) or ``arc`` (one balance per asset with explicit arc flows, the block-angular form). This is a separate, orthogonal axis from the network mode (``NETWORK_MODES``): the network mode is the physics (single node / DC / AC / three-phase), the balance is the bookkeeping, and every balance expresses every network mode -- ``arc`` works with the AC and three-phase modes too (the arc carries active and reactive power and both line ends), and the branch-flow modes are arc-based by construction. ``apply_flag_defaults`` seeds the default, ``select_balance_mode`` / ``balance_compatible_with_network`` validate, and the model build rejects ``arc`` with a clear message (only ``nodal`` is wired in-core; the arc form is the planned modernization, same optimum but ~4x slower monolithic). Tested by ``tests/test_features.py``. See ``docs/decomposition.md`` section 3.
- Stochastic-MILP decomposition benchmark (``benchmarks/milp_decomposition.py``) -- the case where Benders beats the monolith. A unit-commitment problem with first-stage commitment binaries (two conflicting reserve knapsacks, energy and ramp) and a per-scenario dispatch LP as recourse. The monolith's branch-and-bound re-solves the whole S-scenario LP at every node, so it grows super-linearly with the scenario count; Benders keeps the binaries in a small master and the dispatch in per-scenario LP subproblems, growing about linearly. On HiGHS they reach the same optimum and cross near 20 scenarios -- Benders is 1.4x faster at 40 scenarios and 1.6x at 160, with the gap widening. This is the complement to the LP results: decomposition pays when the first stage is combinatorial and its monolith nodes drag the whole second stage along. See ``docs/decomposition.md`` section 3.
- Spatial decomposition benchmark (``benchmarks/spatial_decomposition.py``). Decomposes the block-angular form -- a ring of regions weakly coupled by tie-lines -- as a Benders solve (tie-line flows in the master, one subproblem per region, reusing ``benders_solve``) and compares it to the nodal monolith. It reaches the same optimum and converges in two iterations (the structure is favourable), but it does not beat the monolith: it is 5-20x slower and falls further behind with scale, because it is overhead-bound -- each of the ~2R subproblem solves is a separate Pyomo/HiGHS round-trip, while the monolith is one efficient solve. The honest takeaway: the block-angular structure helps convergence, but a wall-clock win needs the per-block work to dominate the coordination overhead -- intractable (memory-bound) problems or MILP, not moderate LP. See ``docs/decomposition.md`` section 3.
- Nodal vs per-asset/arc balance benchmark (``benchmarks/balance_formulation.py``). It builds the same synthetic multi-period transmission-and-storage model both ways -- one balance per node, versus one injection variable and balance per asset with the node reduced to a flow-conservation sum -- and solves each monolithically, checking the objective matches. The arc form reaches the same optimum but is about three times the variables, five times the constraints and roughly four times slower to solve as one block, consistently across sizes. So the per-asset/arc balance is not a head-on solver speed-up; its value is the block-angular structure it exposes for decomposition (and its modularity / multi-vector reach). Any solving-time advantage comes from decomposing that structure, not from the reformulation itself. See ``docs/decomposition.md`` section 3.
- Temporal Benders solve for el1xr (``oM_Decomposition.el1xr_temporal_benders``), validated against the monolith. It splits one (period, scenario) operating horizon into time blocks coupled by the storage inventory at each boundary: the master holds the investment and the boundary inventory levels, and one windowed operating block per time block has the investment and its incoming/outgoing boundary inventory fixed (the fixing-constraint duals give the cuts). The per-scenario fixed network charge does not split by time window, so it is counted once in the master and removed from each block's recourse; the peak / net-use-var / energy-tax costs are zero on the home cases (no grid import) and do not arise. Two points were needed for an exact match: the boundary coupling is kept hard so inventory is conserved across the split (an elastic boundary lets the block leak inventory and undercut the monolith), and the master's boundary inventory is bounded by the storage capacity so the hard tie is always reachable. Reproduces the monolithic optimum exactly for 2, 3 and 4 time blocks (``tests/test_benders_temporal_el1xr.py``). The peak-demand threshold-LP decomposition for a transmission-import case is the remaining extension (the peak is a top-N horizon-wide selection; the home cases do not import). See ``docs/decomposition.md``.
- el1xr storage-boundary temporal mechanics, validated per-level (``tests/test_benders_temporal_el1xr.py``). Splitting one operating horizon into time blocks couples them through the storage inventory at the boundary. The test solves the monolith, splits the horizon into two windows, and fixes the boundary inventory (and investment) to the monolith's values -- the outgoing inventory on window 1's last level, the incoming inventory replacing window 2's first-level balance -- then checks the two windows reproduce the monolith's per-level operating cost exactly (electricity and hydrogen storage, hourly cycle). This validates the windowed build and the boundary-inventory stitching. It also pins down what is left: el1xr's per-scenario aggregate costs (peak demand, fixed network charge, energy tax -- the ``"ps"`` cost kind) depend on the whole horizon and do not split by window, so they must be handled at the master (the peak as a linking variable across windows, the fixed charge once) for the full temporal solve to match the monolith. See ``docs/decomposition.md``.
- Temporal (storage-boundary) Benders decomposition, validated. Splitting one operating horizon into contiguous time blocks couples the blocks sequentially through the storage inventory carried across each boundary. Putting those boundary inventory levels in the master (as linking variables, like investment, but each shared by only two adjacent blocks) makes it a Benders decomposition that needs no new solver: ``benders_solve`` already handles it, because a temporal subproblem depends on just its two boundary states. Validated against the monolithic optimum on a small multistage storage problem in ``tests/test_benders_temporal.py`` (cyclic storage, elastic blocks for feasibility cuts), the temporal analogue of ``tests/test_benders.py``. Wiring it into el1xr -- a windowed block build plus a mutable incoming-inventory parameter in place of the constant initial inventory -- is the remaining step; the design is in ``docs/decomposition.md``.
- Parallel Benders subproblem solve. The per-(period, scenario) subproblems are independent given the investment decision, so each Benders iteration can solve them at once. Pyomo solvers are not thread-safe (shared writer / tempfile / solver state — a thread pool deadlocks after the first solve), so the parallelism is by process: with ``BendersConfig.n_workers > 1`` ``el1xr_benders`` starts a pool of worker processes, each of which builds and owns a round-robin slice of the blocks once and reuses them across iterations; the master sends the trial investment over a pipe and collects each block's cost and duals. ``benders_solve`` stays generic via an optional ``solve_blocks`` callback (sequential, ``n_workers = 1``, is unchanged and remains the default). The result is identical to the sequential solve. Measured on a 12-CPU machine with Gurobi for an 8-block case: about 1.6x at 2 workers, 2.6x at 4, 3.0x at 8 (the same optimum every time); the speed-up flattens past four workers because of the one-time full build still done to read the investment structure. Validated by ``tests/test_benders_el1xr.py``; ``tests/_par_bench.py`` is the benchmark script.
- el1xr Benders wiring (``oM_Decomposition.el1xr_benders``) and a reusable build seam (``oM_Sequence.build_model``, the build half of ``routine``). ``el1xr_benders`` constructs the investment master and, per (period, scenario) block, an operating subproblem restricted to that scenario (built via the new ``_build_block`` helper, which reuses the validated full build with the other scenarios' probability zeroed) with the investment variables fixed, then calls the generic ``benders_solve``. The el1xr operating model is not complete-recourse with respect to investment (too little investment can make a block infeasible), which an optimality-cut-only loop cannot steer away from; each subproblem therefore adds a penalised slack to every operating constraint except the investment-fixing ones, so the block is always feasible and any infeasibility becomes a feasibility (steering) cut. The penalty is large vs any real operating cost, so at the optimum no slack is used. Validated to reach the exact monolithic optimum on a two-scenario case (``tests/test_benders_el1xr.py``); the penalty is configurable via ``BendersConfig.extra["feasibility_penalty"]``. See ``docs/decomposition.md``.
- Generic Benders decomposition solver (``oM_Decomposition.benders_solve``, architecture Stage D). A multi-cut L-shaped method that splits a two-stage problem into a master (first-stage decisions plus recourse cost-to-go variables) and one subproblem per block, adding optimality cuts from the subproblem duals until the bound gap closes. The interface is callback-based (the subproblem carries a free copy of the first-stage variables fixed to the master values, and the duals of those fixing constraints give the cut), so it works for any two-stage stochastic program and is the template for the el1xr investment/operating split. Validated against the monolithic optimum on a small stochastic capacity-expansion problem (same structure as el1xr: build capacity, then dispatch per scenario with an energy-not-served penalty) - Benders reaches the exact optimum in a few iterations (``tests/test_benders.py``). The el1xr-specific wiring is ``el1xr_benders`` (see above); parallel subproblem solving is a follow-on (the subproblems are independent).
- Unbalanced linear OPF (``oM_LinDist3Flow.py``, architecture Stage C). LinDist3Flow is the linearised three-phase branch-flow model: per-phase squared voltages and flows on a radial feeder with a linear voltage-drop law that keeps the 3x3 phase coupling to first order. It is an **LP** — so it is built and solved in Python (HiGHS) and could be built by linopy — and is the linear, in-Python unbalanced option, distinct from the exact unbalanced AC OPF (NLP/SOCP, the PowerModelsDistribution.jl path of Phase 5c). A standalone analysis module like ``oM_ACOPF`` (does not touch the main model). Validated on a radial feeder: a balanced feeder with diagonal impedance reduces phase by phase to the single-phase LinDistFlow (exact), and unbalanced loading produces the expected per-phase voltage spread. A network-mode catalogue in ``oM_Features`` (``NETWORK_MODES``) records each network representation (single_node / dc / distflow_socp / acopf_nlp / lindist3flow) with its problem class and whether it is in-core or a decoupled analysis. Tested by ``tests/test_lindist3flow.py``.
- Feature catalogue and problem-class logic (``oM_Features.py``, architecture Stages A and B). One place that (i) lists the optional features and their option flags with safe defaults — so a case whose Option file predates a flag still runs instead of raising ``KeyError`` (``apply_flag_defaults``, replacing the scattered per-flag defaults); (ii) detects the model's mathematical class (LP / MILP / QP / MIQP / SOCP / MISOCP / NLP) from the built model and checks the chosen solver can handle it, logging which solvers and model-building libraries support that class (the capability matrices from the framework study); and (iii) provides a cost/revenue registry so a new cost-bearing feature registers its term (``register_cost`` / ``register_revenue``) instead of editing the objective-aggregation rules. The objective aggregation now sums the registry, seeded with the built-in terms in their original order, so existing results are unchanged. The problem class is the lever for choosing both the solver and (for a future migration) the build library: e.g. a MISOCP case rules out HiGHS and linopy. Tested by ``tests/test_features.py`` and ``tests/test_problem_class.py``.
- AC optimal power flow module (``oM_ACOPF.py``, Phase 5a). A standalone, single-phase analysis that runs on a network snapshot (the case's electricity-network branches plus nodal injections), decoupled from the main solve so it stays tractable. Two formulations: the second-order-cone (branch-flow / DistFlow) relaxation, solved with Gurobi and reporting the relaxation gap, and the exact polar NLP, solved with Ipopt and warm-started from the SOC solution. Validated against the IEEE 33-bus feeder (Baran & Wu): both reproduce the published base-case loss (~202.7 kW) and minimum voltage (~0.913 pu), and agree to 0.001 kW. Results (per-bus voltages and a summary) can be written to a DuckDB file. See ``tests/test_acopf.py`` and ``docs/scope_acopf_community.md``.
- AC OPF multi-snapshot sweep (``oM_ACOPF.run_acopf_sweep``, Phase 5b). Runs one AC OPF per snapshot and summarises voltage/loss violations across a horizon, writing the summary to DuckDB (``oM_Result_ACOPF_Sweep``); ``scaled_snapshots`` builds a load-profile set and ``snapshots_from_case`` pulls per-node demand from a case. On the IEEE 33-bus feeder over a 0.5x-1.3x load profile, losses rise and minimum voltage falls monotonically with load and the base snapshot matches the Phase-5a benchmark.
- Energy-community / virtual-sharing layer (``oM_Community.py``, Phase 6a). Retailers (members) in the same zone can share locally generated electricity before importing from or exporting to the grid, which avoids the retail buy/sell spread and lowers total community cost. It adds two per-member variables (``vEleShareIn``, ``vEleShareOut``), a per-zone pool-conservation constraint, and the matching terms in the retail balance. Enabled with the option flag ``IndBinCommunity``; off by default, so existing cases are unchanged (the four validation cases keep their exact costs). Validated by ``tests/test_community.py``, which builds a two-member community and checks that sharing is used and total cost does not increase.
- Green-hydrogen layer in ``oM_GreenHydrogen.py``: an optional hourly temporal-matching (RFNBO additionality) constraint that caps electrolyser electricity use by the available renewable generation (own units plus PPA-contracted units), enabled with the ``pParGreenH2Matching`` option; and electricity PPA settlement that defines the previously zeroed ``vTotalEleMrkPPACost`` for renewable units flagged ``pEleGenPPA``. Off by default, so existing cases are unchanged.
- Investment (capacity-sizing) layer in ``oM_Investment.py``: build-decision variables for candidate generators and storage, capacity-coupling constraints, and an investment-cost term in the objective. The investment cost is scaled by ``factor1`` (the MWh/kWh unit knob) like the capacities and per-energy operating costs, and weighted by the period discount factors, so it stays on the same unit and discounted footing as operation when switching between utility and home scales. The capacity-expansion formulation follows the openTEPES model (Ramos, Alvarez, and Lumbreras, *openTEPES: Open-source Transmission and Generation Expansion Planning*, SoftwareX 18, 2022, `doi:10.1016/j.softx.2022.101070 <https://doi.org/10.1016/j.softx.2022.101070>`_). For a sizing study the modeled load levels should represent a full year (via period weights and durations) so the annualized investment trades off against a full year of operation. The electrolyser electricity-input sizing is still pending review.
- Small hydrogen-VPP test case in ``data/H2VPP`` (24 load levels) that solve-tests the investment and green-hydrogen layers; solves in about one second. See ``data/H2VPP/README.md``.
- DuckDB input support. A case can now be read from a single ``<case>.duckdb`` file as well as from a CSV folder. The two backends (``oM_InputCSVSource``, ``oM_InputDuckDBSource``) share one interface (``oM_InputSource``: the ``InputSource`` base class, the ``open_source`` / ``resolve_source`` factory, and small shape helpers) and return identical DataFrames, so a DuckDB run reproduces a CSV run exactly. ``oM_InputData`` now reads through this interface instead of reading CSVs directly.
- ``oM_CsvToDuckDB`` converter and the ``el1xr-csv2duckdb`` command, which turns a CSV case folder into a ``<case>.duckdb`` file. The naming rules and the reserved ``__idx`` index columns it uses are described in ``oM_InputSchema``.
- DuckDB results are now written by default to ``<case>/results.duckdb`` (one table per set, parameter, variable and constraint dual, plus a ``oM_Result_RunMetadata`` headline table with the case, date, solver, objective and version). Controlled by the new ``--duckdbresults`` flag (default on); CSV results stay available via ``--rawresults``.
- Heat-sector scaffold (``oM_HeatSector``) and heat input stems in ``oM_InputSchema``. The architecture is now heat-ready (home/residential and district heating); the formulation itself is not built yet and is not called from the solve pipeline.
- Architecture diagram (``docs/img/el1xr_opt_architecture.svg``) and a new Architecture section in the README, plus a note on computational efficiency in ``docs/computational_efficiency.md``.
- Small variant validation cases generated from the H2VPP base by ``data/sizing/make_sizing_cases.py``: home and neighbourhood battery sizing, a power-tariff on/off pair, and frequency-market variants (FCR-D only, FCR-N only, both, none). They are short LP cases (reproducible cost), read as ``.duckdb`` input, and rebuilt by the test fixture rather than committed, so only the generator and its README are tracked. Two hydrogen cases (H2 tank, electrolyser) are included as feasibility cases; they do not yet size anything because the base case does not link the electrolyser as an electricity-to-hydrogen converter. See ``data/sizing/README.md``.

Changed
~~~~~~~

- Continuous integration reworked into two tiers (``.github/workflows/ci.yml``), replacing the single ``conda-build.yml`` job. A fast tier lints and runs the no-solve tests on Linux, macOS and Windows for Python 3.11, 3.12 and 3.13; a solve tier runs the validation cases on the three operating systems for Python 3.12. Validation now covers four cases (Home1, Grid1, EEM26, H2VPP), each solved from both its CSV folder and its ``.duckdb`` file and checked against a golden cost.
- CI validation cases are solved over one week of operation (168 load levels) instead of a month. One week is enough to exercise the model in tests, and it cuts the full test-suite run from about six minutes to two. Full-year "proper" runs are meant for a larger machine, not CI.

Fixed
~~~~~

- Multi-period / multi-scenario models could not be built at all: the initial-output and initial-commitment parameters (``pEleInitialOutput`` / ``pEleInitialUC`` and the hydrogen analogues in ``oM_InputData``) were sized by the number of units instead of (period x scenario x units), which only matched for a single (period, scenario). They are now sized correctly, so cases with more than one period or scenario build. Single-(period, scenario) cases are unaffected (the four validation cases keep their exact costs). This is what unblocks the Benders decomposition over (period, scenario) blocks. Regression: ``tests/test_benders_el1xr.py``.
- Corrected the ``model.psnesc`` index set in ``oM_InputData.py`` (it used ``model.psc`` instead of ``model.psn``, so it produced 3-tuples that could not be unpacked). The set is built only when investment candidates exist, so the error surfaced the first time a case included a candidate unit.
- Import the output modules (``oM_OutputData``, ``oM_OutputData_duckdb``) lazily inside ``routine`` instead of at the top of ``oM_Sequence``. This keeps the heavy plotting libraries out of the package import path, so the documentation build can import the package and generate the API reference without them, and it removes an import cycle that broke the docs build on Python 3.11.
- Build the ordered load-level list once in ``create_constraints`` instead of rebuilding it on every constraint-rule call. The slicing is identical, so results are unchanged; this removes a quadratic-scaling cost that showed up on cases with long storage cycles or long minimum up/down times.
- The solve tests back up and restore the ``Duration`` input file byte for byte, so running the test suite no longer leaves the tracked CSV cases reformatted.
- The DuckDB read and write paths use DuckDB's relational API (``connection.table(...)`` and ``from_df(...).create(...)``) instead of building SQL strings with table names, so no identifier is ever interpolated into a query. This removes the static-analysis "possible SQL injection" warnings and is the safer pattern. Removed the small-file ``block_size`` option (it only mattered for committing case files, which are now generated on the fly).
- Fixed the electricity-to-hydrogen (``e2h``) path, which had never run because no shipped case had an active hydrogen generator. Defined the missing ``model.hgr`` set (the hydrogen analogue of the electricity RES set ``egr``, empty since there is no hydrogen RES column) so the initial-output loop no longer raises ``AttributeError``; and guarded two electricity-storage code paths (variable inflow/outflow/inventory bounds in ``oM_InputData`` and the ``eEleTotalMaxChargeConditioned`` constraint in ``oM_ModelFormulation``) so electrolysers, which also consume electricity, are no longer treated as storage. With these fixes a case with an electrolyser builds and solves, and hydrogen storage can be sized.
